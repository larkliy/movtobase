    Структура NativeAOT: как C# превращается в один нативный бинарник¶

    Обычный .NET тащит с собой JIT: IL лежит в сборках, а машинный код рождается на ходу, при первом вызове метода. NativeAOT выворачивает это наизнанку. Компиляция целиком происходит на этапе сборки, IL больше не нужен, JIT в рантайме нет вообще. На выходе один нативный исполняемый файл, который стартует как C++ программа и не требует установленного .NET.

    Разберем, из чего эта штука собрана. В репозитории есть две большие половины: компилятор в src/coreclr/tools/aot и рантайм с урезанной библиотекой в src/coreclr/nativeaot.

    На пальцах: что вообще происходит¶

    Представьте две столовые. Первая держит повара, который готовит каждое блюдо только когда его заказали. Плюс: меню бесконечное, повар подстраивается под гостя. Минус: каждый заказ ждать, а повар занимает место на кухне. Это JIT.

    Вторая столовые привозит еду уже готовой в контейнерах. Плюс: подал на стол мгновенно, повар не нужен. Минус: меню зафиксировано заранее, и все, что не положили в контейнер, гость не получит. Это NativeAOT.

    Разница в том, когда происходит превращение C# в машинный код. Обычный .NET компилирует C# в промежуточный байт-код под названием IL. IL - это не машинный код, а что-то вроде универсальной инструкции для виртуальной машины: "положи на стек", "сложи", "вызови метод". При запуске JIT читает IL метода и на ходу переводит его в инструкции конкретного процессора.

    NativeAOT переводит весь IL в машинный код заранее, при сборке. В готовом бинарнике нет ни IL, ни JIT. Есть обычный машинный код, как будто программу написали на C++.

    Вот как выглядит один и тот же код в обоих мирах. Возьмем такой C#:

    static int Add(int a, int b) => a + b;

static void Main()
{
    int sum = Add(2, 3);
    Console.WriteLine(sum);
}

    При JIT происходит так. Компилятор C# кладет в сборку IL метода Add:

    .method static int32 Add(int32 a, int32 b)
{
    ldarg.0        // положить a на стек
    ldarg.1        // положить b на стек
    add            // сложить два верхних значения
    ret            // вернуть результат
}

    При первом вызове Add рантайм замечает, что у метода еще нет машинного кода, зовет JIT, тот выдает что-то вроде:

    lea eax, [rcx + rdx]   ; eax = a + b
ret

    и только потом вызов выполняется. При NativeAOT этот lea/ret уже лежит в бинарнике с самого начала, а IL из сборок можно выбросить. JIT в рантайме просто нет.

    Теперь важный момент, из которого растет все остальное. Раз JIT нет, код нельзя дооптимизировать в рантайме. Зато компилятор в момент сборки видит всю программу целиком и может позволить себе то, что JIT не может: выбросить неиспользуемое, заменить виртуальные вызовы прямыми, посчитать статику заранее. Этим и объясняется большая часть архитектуры, которую мы разбираем.

    Словарь терминов¶

    Дальше по тексту будут встречаться слова, которые стоит расшифровать сразу. Сюда можно возвращаться.

    AOT (Ahead-Of-Time) - компиляция заранее, до запуска программы. Противоположность JIT.

    JIT (Just-In-Time) - компиляция в момент выполнения, при первом вызове метода.

    IL (Intermediate Language) - промежуточный байт-код, в который компилятор C# превращает ваш код. Не машинный код, а описание операций для виртуальной машины.

    ILC (IL Compiler) - компилятор NativeAOT. Читает IL и выдает машинный код и объектные файлы.

    RyuJIT - бэкенд кодогенерации, который превращает IL в машинные инструкции. Его использует и CoreCLR (в рантайме), и ILC (на этапе сборки). Один и тот же движок, разное время вызова.

    Root (корень компиляции) - точка, с которой начинается обход программы. Все, что достижимо от корней, попадает в бинарник.

    Dependency graph (граф зависимостей) - модель "кто кого использует". Узлы - типы и методы, ребра - ссылки между ними. Компилятор обходит его от корней.

    Trimming (тримминг) - удаление всего, что не достижимо от корней.

    Scanner (сканер) - предварительный проход по IL до настоящей кодогенерации. Собирает факты: что создается, что вызывается, что можно оптимизировать.

    Devirtualization (девиртуализация) - замена виртуального вызова (через таблицу) на прямой вызов конкретного метода, когда компилятор доказал, что других вариантов нет.

    Method table (MethodTable) - структура, описывающая тип: размер объекта, флаги, базовый тип, список интерфейсов, vtable. В CoreCLR ее называют MethodTable, в старых текстах про .NET Native - EEType. Это одно и то же.

    Vtable (таблица виртуальных методов) - массив указателей на методы, который лежит сразу за заголовком MethodTable. По индексу в этом массиве работает виртуальный вызов.

    TypeManager - объект рантайма, соответствующий одному скомпилированному модулю. Знает про method table'ы, generic-словари и статику своего модуля. Аналог модуля в CoreCLR.

    Bookend - пара символов-маркеров ("закладка") начала и конца секции. Линкер склеивает все куски одной секции между закладками, и рантайм получает непрерывный диапазон.

    Classlib - базовая библиотека классов: Object, String, Array и так далее. У NativeAOT есть своя минимальная classlib, Runtime.Base.

    PAL (Platform Abstraction Layer) - слой, который прячет различия между Windows и Unix под общим API. Чтобы код рантайма не был усыпан #ifdef.

    EH (Exception Handling) - обработка исключений. В NativeAOT устроена иначе, чем в CoreCLR, и завязана на диапазоны управляемого кода.

    Stack walking - обход стека вызовов: от текущего кадра к вызывающему и так далее. Нужен для stack trace, исключений и сборки мусора.

    Bump pointer - аллокация сдвигом указателя: "взять текущую позицию, сдвинуть на размер, вернуть старое значение". Самый быстрый способ выделить память.

    Tiered compilation - многоуровневая JIT-компиляция: сначала быстрый неоптимизированный код, потом, для горячих методов, оптимизированный. У NativeAOT этого нет.

    PGO (Profile-Guided Optimization) - оптимизация на основе профиля реального выполнения. JIT может собрать профиль на ходу, ILC - только заранее, из внешних данных.

    rd.xml - XML-файл, в котором перечисляют типы, нужные рефлексии, чтобы тримминг их не выбросил.

    Vector - аппаратно-ускоренный векторный тип. JIT подбирает его размер под процессор в рантайме, ILC обязан решить это на этапе сборки.

    Sync block / thin lock - служебные данные в заголовке объекта: хэш-код, тонкая блокировка, индекс записи в таблице синхронизации.

    Blittable - тип, у которого управляемое и нативное представление в памяти совпадают, поэтому его можно передавать в нативный код без конвертации.

    FCIMPL / HCIMPL - макросы, которыми в рантайме объявляют нативные функции, вызываемые из управляемого кода. FCIMPL1 означает "один аргумент".

    HANDLE - дескриптор, непрозрачный числовой идентификатор ресурса ОС (модуля, потока и т.д.).

    Две половины¶

    Компилятор (ILC) живет в src/coreclr/tools/aot. Ключевые проекты:

    • ILCompiler - точка входа, разбор командной строки, оркестрация.
    • ILCompiler.Compiler - сам компилятор: dependency analysis, code generation.
    • ILCompiler.TypeSystem - собственная модель типов, не зависящая от рантайма.
    • ILCompiler.RyuJit - бэкенд кодогенерации, тот же RyuJIT, что и в CoreCLR.
    • ILCompiler.DependencyAnalysisFramework - движок графа зависимостей.

    Рантайм живет в src/coreclr/nativeaot:

    • Bootstrap - нативный C++ main, который запускает все.
    • Runtime - нативный рантайм на C++: GC-интеграция, потоки, EH, stack walk, type manager.
    • Runtime.Base - минимальная управляемая библиотека (Object, String, Array, Exception), которая компилируется прямо в рантайм.
    • System.Private.CoreLib - настоящая CoreLib для NativeAOT.
    • Common - общий код между компилятором и рантаймом: MethodTable, StartupCodeHelpers.
    • System.Private.TypeLoader, System.Private.Reflection.Execution - загрузка типов и рефлексия.

    Важно понять разделение труда. Компилятор - это обычная .NET-программа, которая запускается на вашей машине при dotnet publish. Она читает сборки и генерирует объектные файлы. Рантайм - это C++ код, который компилируется нативным компилятором (MSVC, clang, gcc) и линкуется вместе с этими объектными файлами. Дальше эти две части встречаются только в готовом бинарнике.

    Проект Common - это то, что нужно обеим половинам. Например, MethodTable должен быть описан одинаково и в компиляторе (чтобы генерировать правильные данные), и в рантайме (чтобы их читать). Поэтому общий код лежит в Common/src/Internal/Runtime и подключается к обоим.

    Еще полезно держать в голове такую аналогию. Компилятор - это проектировщик, который составляет чертеж дома. Рантайм - это фундамент и коммуникации, которые уже стоят на участке. Линкер - это стройка, которая сводит чертеж и фундамент вместе.

    Пайплайн компиляции¶

    Точка входа компилятора - Program.Run (ILCompiler/Program.cs:72). Порядок примерно такой.

    Сначала создается контекст системы типов (Program.cs:126):

    CompilerTypeSystemContext typeSystemContext =
    new CompilerTypeSystemContext(targetDetails, genericsMode, supportsReflection ? DelegateFeature.All : 0,
        genericCycleDepthCutoff: Get(_command.MaxGenericCycleDepth),
        genericCycleBreadthCutoff: Get(_command.MaxGenericCycleBreadth));

    Это отдельный, самостоятельный type system. Он читает входные сборки и reference-сборки, но ничего не знает про CoreCLR. Компилятор должен уметь ответить на любой вопрос о типах сам, потому что в рантайме спросить будет некого.

    Что такое "type system" в этом контексте. Это программная модель, которая отвечает на вопросы о типах: какой у типа базовый класс, какие поля, какой размер, какие методы, совместим ли один тип с другим. В CoreCLR такая модель встроена в рантайм, потому что типы могут подгружаться на ходу. У компилятора она своя, потому что все типы известны заранее и рантайм ему недоступен.

    Что такое "reference-сборки". Это сборки-заглушки, в которых есть только сигнатуры, без реализации. Они нужны, чтобы компилятор знал, как выглядят типы из платформы, но не тащил в анализ чужой код. Скажем, System.Runtime.dll из reference pack говорит "есть тип System.String с такими-то методами", и этого достаточно для проверки типов.

    Дальше собираются корни компиляции (Program.cs:171). Root - это то, с чего начинается обход графа: метод Main, инициализаторы библиотек, точки входа UnmanagedCallersOnly, типы из rd.xml. Все, что достижимо от корней, попадет в бинарник. Все, что нет, будет выброшено. Это и есть тримминг, только тотальный.

    Вот как это выглядит на примере. Пусть программа такая:

    class Program
{
    static void Main()
    {
        Console.WriteLine(Greeting());
    }

    static string Greeting() => "hello";

    static void NeverCalled() => Console.WriteLine("dead code");
}

    Корень - Main. От него граф тянется к Console.WriteLine и Greeting. Метод NeverCalled ни от кого не достижим, значит его машинного кода в бинарнике не будет вообще. Если бы это была библиотека, корнями были бы еще и все публичные API, помеченные как экспортируемые.

    Что такое "граф зависимостей" и зачем он нужен. Компилятор не может просто пройтись по всем методам подряд: тогда он сгенерирует код для того, что никогда не вызовется. Вместо этого он строит граф: "метод A вызывает метод B", "метод B создает тип C", "тип C содержит поле типа D". Обход от корней по этому графу дает точный список всего нужного. Это и есть тот самый whole-program view, которого нет у JIT.

    Схематично:

    Main
 ├── Console.WriteLine
 └── Greeting
       └── (возвращает string)

NeverCalled          <- ни одного входящего ребра, выброшен

    Потом запускается сканер (Program.cs:510). Он проходит по всему графу в режиме интерпретации IL и собирает факты: какие типы реально создаются, какие методы реально вызываются, какие интерфейсные вызовы можно девиртуализировать, какие статические поля можно прединициализировать. Результаты сканера отдаются билдеру (Program.cs:552):

    builder.UseVTableSliceProvider(scanResults.GetVTableLayoutInfo());
builder.UseGenericDictionaryLayoutProvider(scanResults.GetDictionaryLayoutInfo());
builder.UseDevirtualizationManager(devirtualizationManager);
builder.UseInliningPolicy(scanResults.GetInliningPolicy());

    Вот где NativeAOT выигрывает. Компилятор видит всю программу целиком. Если тип ни разу не был создан, его method table можно не генерировать. Если метод никто не переопределяет, вызов становится прямым. Это то, чего JIT не может, потому что он компилирует методы по одному и не знает будущего.

    Разберем девиртуализацию подробнее, потому что это самый наглядный выигрыш. Пусть есть интерфейс и одна реализация:

    interface IShape { double Area(); }

class Circle : IShape
{
    public double Radius;
    public double Area() => Math.PI * Radius * Radius;
}

class Program
{
    static double Total(IShape s) => s.Area() * 2;

    static void Main()
    {
        var c = new Circle { Radius = 1.0 };
        Console.WriteLine(Total(c));
    }
}

    JIT видит метод Total(IShape s) и не знает, что в него передадут. Значит, он генерирует виртуальный вызов: смотрит на реальный тип объекта в рантайме, идет в его vtable, берет указатель на Area и вызывает. Это лишняя загрузка и косвенный переход.

    Компилятор NativeAOT проходит по графу и обнаруживает, что Circle - единственная реализация IShape, и объект создается только как Circle. Значит, вызов s.Area() можно заменить на прямой вызов Circle.Area:

    // было
static double Total(IShape s) => s.Area() * 2;

// после девиртуализации компилятором (схематично)
static double Total(IShape s) => Circle.Area((Circle)s) * 2;

    Выигрыш двойной: исчезает косвенный переход, и открывается дорога к инлайну. JIT тоже умеет девиртуализировать, но только когда видит профиль или локальный контекст, а не всю программу.

    Еще один трюк - прединициализация статики. Если статическое поле можно вычислить на этапе сборки, компилятор посчитает его и положит в бинарник готовое значение, вместо того чтобы выполнять код при старте. Например:

    static readonly int[] Primes = ComputePrimes();

    Если ComputePrimes детерминирована и не зависит от внешних данных, ILC может выполнить ее во время сборки и записать результат прямо в данные. Рантайм тогда ничего не считает.

    Сама кодогенерация идет через RyuJitCompilationBuilder (Program.cs:366), который внутри вызывает тот же RyuJIT, что и CoreCLR. Разница в том, что здесь он вызывается на этапе сборки, а не в рантайме. Финальный шаг:

    ICompilation compilation = builder.ToCompilation();
CompilationResults compilationResults = compilation.Compile(tempOutputFilePath, ObjectDumper.Compose(dumpers));

    Compile (Program.cs:654) выдает набор объектных файлов, которые потом линкуются с рантаймом в один бинарник.

    Точка входа: bootstrap¶

    Нативный main лежит в Bootstrap/main.cpp. Именно он первым получает управление. Есть два режима: обычное приложение и нативная библиотека (DLL). Вот как выбирается точка входа (main.cpp:179):

    #ifndef NATIVEAOT_DLL
#define NATIVEAOT_ENTRYPOINT __managed__Main
...
extern "C" int __managed__Main(int argc, wchar_t* argv[]);
#else
#define NATIVEAOT_ENTRYPOINT __managed__Startup
extern "C" void __managed__Startup();
#endif

    __managed__Main - это ваш Main, скомпилированный в нативный код с C-соглашением о вызовах. Для рантайма это обычная extern-функция.

    Разберемся с терминами в этом фрагменте. extern "C" в C++ отключает искажение имен (name mangling). Компилятор C++ обычно превращает имя Foo(int) в нечто вроде _Z3Fooi, чтобы поддерживать перегрузки. Для линковки с кодом, где таких правил нет, нужно extern "C": тогда имя остается Foo. Именно поэтому управляемые точки входа получают предсказуемые имена, которые ищет линкер.

    "Соглашение о вызовах" (calling convention) - это правила о том, кто кладет аргументы в регистры, кто чистит стек, кто восстанавливает регистры. У __managed__Main на Windows x64 это __cdecl, на других платформах обычное системное. Компилятор ILC генерирует функцию ровно по этим правилам, чтобы нативный main мог ее вызвать, ничего не зная про .NET.

    Что происходит по шагам, когда вы запускаете бинарник:

    ОС
 └── вызывает main() из Bootstrap/main.cpp
       └── InitializeRuntime()
             ├── RhInitialize()          // поднять PAL, рантайм, GC
             ├── RhRegisterOSModule()    // отдать диапазоны кода и таблицу classlib
             └── InitializeModules()     // создать TypeManager'ы, зарегистрировать модули
       └── вызывает __managed__Main()    // это ваш Main
             └── ... ваш код ...

    Никакой магии: нативный main просто вызывает управляемую функцию как обычную C-функцию. Все, что делает NativeAOT, - заранее превращает Main в такую функцию.

    Инициализация (main.cpp:190):

    static int InitializeRuntime()
{
    if (!RhInitialize(/* isDll */ false))
        return -1;

    void * osModule = PalGetModuleHandleFromPointer((void*)&NATIVEAOT_ENTRYPOINT);

    if (!RhRegisterOSModule(
        osModule,
        (void*)&__managedcode_a, (uint32_t)((char *)&__managedcode_z - (char*)&__managedcode_a),
        (void*)&__unbox_a, (uint32_t)((char *)&__unbox_z - (char*)&__unbox_a),
        (void **)&c_classlibFunctions, _countof(c_classlibFunctions)))
    ...
    InitializeModules(osModule, __modules_a, (int)((__modules_z - __modules_a)), ...);
    return 0;
}

    Здесь интересна механика с bookends. ILC генерирует объектные файлы с секциями, а линкер склеивает их в непрерывные диапазоны. __managedcode_a и __managedcode_z - маркеры начала и конца всего управляемого кода. Тот же трюк с .modules для списка модулей и .unbox для unboxing-стабов (main.cpp:25, main.cpp:54, main.cpp:65).

    Поясню, что такое секция и линкер, потому что это ключ ко всему механизму. Объектный файл - это результат компиляции одного файла кода. Внутри он разбит на секции (их еще называют сегментами): код в одной, данные в другой, константы в третьей. Линкер - это программа, которая собирает объектные файлы в один исполняемый и раскладывает их секции по памяти.

    Фокус в том, что линкер склеивает одноименные секции. Если у нас есть объектные файлы a.obj, b.obj, c.obj, и в каждом есть секция .managedcode, то линкер положит их подряд в одну общую секцию. А если задать специальные имена вида .managedcode$A и .managedcode$Z, линкер положит их по алфавиту: $A окажется в начале, $Z в конце. Получаются те самые "закладки":

    .managedcode$A   -> символ __managedcode_a
  a.obj: метод Main
  b.obj: метод Greeting
  c.obj: метод Console.WriteLine
.managedcode$Z   -> символ __managedcode_z

    Теперь, зная адреса __managedcode_a и __managedcode_z, рантайм знает, где начинается и где заканчивается весь управляемый код, хотя каждый метод лежал в отдельном объектном файле. Секция .unbox устроена так же, только для unboxing-стабов, а .modules - для указателей на данные модулей.

    Этот трюк не уникален для .NET. Ровно так же C++ компиляторы собирают список глобальных конструкторов: каждый файл кладет свой указатель в секцию .CRT$XCU, а линкер склеивает их в один массив, который выполняется при старте.

    Рантайму эти диапазоны нужны, чтобы понимать, где управляемый код. Вот как это используется (Runtime/RuntimeInstance.cpp:95):

    bool RuntimeInstance::IsManaged(PTR_VOID pvAddress)
{
    return (dac_cast<TADDR>(pvAddress) - dac_cast<TADDR>(m_pvManagedCodeStartRange) < m_cbManagedCodeRange);
}

    Проверка адреса на попадание в управляемый код нужна для stack walking, разбора исключений и поиска method info по return address.

    Еще один важный кусок - таблица функций classlib (main.cpp:150). Рантайм не знает, как создать исключение или разрешить интерфейсный вызов, потому что это управляемый код. Поэтому bootstrap передает ему указатели:

    static const pfn c_classlibFunctions[] = {
    &MANAGED_RUNTIME_EXPORT_NAME(GetRuntimeException),
    &MANAGED_RUNTIME_EXPORT_NAME(RuntimeFailFast),
    (pfn)&ThreadEntryPoint,
    &MANAGED_RUNTIME_EXPORT_NAME(AppendExceptionStackFrame),
    &MANAGED_RUNTIME_EXPORT_NAME(ResolveDispatch),
    ...
};

    Это разрыв циклической зависимости: нативный рантайм дергает управляемые функции через таблицу указателей, а не через линковку.

    Почему здесь вообще цикл. Рантайму нужно уметь бросить исключение, а исключение - это управляемый объект, для которого нужна classlib. Но classlib сама написана на C# и зависит от рантайма. Получается замкнутый круг: чтобы создать исключение, нужен рантайм, а чтобы рантайм работал, нужна classlib.

    Решение - инверсия зависимости. Рантайм ничего не знает о конкретных управляемых функциях. Он знает только, что по индексу N в переданной таблице лежит указатель на функцию создания исключения. Управляемая сторона заполняет таблицу своими методами и отдает ее рантайму при старте. Кто кого вызывает, решается в рантайме, а не на этапе линковки.

    Вот что лежит в таблице и зачем:

    • GetRuntimeException - создать объект исключения по идентификатору (например, NullReferenceException).
    • RuntimeFailFast - аварийно завершить процесс, когда продолжать нельзя.
    • ThreadEntryPoint - точка входа для нового потока, чтобы поток начал выполнять управляемый код.
    • AppendExceptionStackFrame - добавить кадр в строящийся stack trace при разборе исключения.
    • ResolveDispatch - разрешить интерфейсный вызов, когда компилятор не смог девиртуализировать его заранее.

    Индекс в таблице и идентификатор совпадают с перечислением ClassLibFunctionId в управляемом коде (InternalCalls.cs:20):

    Рантайм¶

    RhInitialize (Runtime/startup.cpp:349) инициализирует PAL, ставит обработчик выхода и зовет InitDLL (startup.cpp:87). Внутри:

    static bool InitDLL(HANDLE hPalInstance)
{
    InitializeGCEventLock();
    ...
    if (!RestrictedCallouts::Initialize())
        return false;
    if (!RuntimeInstance::Initialize(hPalInstance))
        return false;
    ...
    if (!InitializeGC())
        return false;
    ...
    if (!DetectCPUFeatures())
        return false;
    ...
}

    Разберем термины из этого кода. PAL (Platform Abstraction Layer) - это тонкий слой над системными API. Вместо того чтобы в каждом месте писать "на Windows вызови VirtualAlloc, а на Linux mmap", рантайм вызывает PalVirtualAlloc, а PAL уже внутри разбирается, что делать. Благодаря этому код RuntimeInstance и GCHelpers выглядит одинаково на всех платформах.

    FCIMPL4 в объявлении RhpCreateTypeManager - это макрос, который разворачивается в правильное объявление нативной функции, вызываемой из управляемого кода. Цифра - количество аргументов. Рантайм использует такие макросы, чтобы не повторять вручную соглашение о вызовах, переход в кооперативный режим GC и проверки на каждом вызове.

    Порядок критичен: сначала базовое состояние рантайма, потом GC, потом проверка CPU. DetectCPUFeatures (startup.cpp:166) сверяет набор инструкций процессора с g_requiredCpuFeatures, который зашил компилятор. Если бинарник собран под AVX2, а процессор его не умеет, приложение упадет сразу с внятным сообщением, а не через полчаса на случайной инструкции. Это плата за статическую кодогенерацию.

    Почему проверка CPU идет после GC, а не раньше. Потому что сообщение об ошибке нужно как-то напечатать, а для этого уже нужен работающий рантайм и память. Поэтому сначала поднимается минимум, и только потом проверяются инструкции.

    RuntimeInstance (RuntimeInstance.cpp:303) - центральный объект рантайма. Он хранит список TypeManager'ов, диапазон управляемого кода, список unboxing-стабов. Через него регистрируются модули:

    FCIMPL4(TypeManagerHandle, RhpCreateTypeManager, HANDLE osModule, void* pModuleHeader, ...)
{
    TypeManager * typeManager = TypeManager::Create(osModule, pModuleHeader, pClasslibFunctions, nClasslibFunctions);
    GetRuntimeInstance()->RegisterTypeManager(typeManager);
    return TypeManagerHandle::Create(typeManager);
}

    TypeManager - это аналог модуля в CoreCLR: он знает про свои method table'ы, generic-словари и статические данные.

    Проведем аналогию. В CoreCLR модуль - это загруженная сборка. Рантайм может в любой момент попросить ее: "дай тип с таким именем". В NativeAOT сборок в привычном смысле нет, но есть скомпилированные модули, и у каждого - свой TypeManager, который знает все свои типы статически. Разница в том, что CoreCLR ищет тип динамически, а TypeManager читает уже готовые структуры, которые положил компилятор.

    Еще одна важная задача рантайма - stack walking, то есть обход стека вызовов. Чтобы пройти от текущего метода к вызывающему, нужно понять, где в стеке лежит обратный адрес, какие регистры сохранены и какого размера кадр. Для этого рантайм использует GC info - метаданные, которые компилятор сгенерировал для каждого метода и которые говорят, где на каждом участке кода живут ссылки и как восстановить стек.

    Это нужно для трех вещей: собрать stack trace при исключении, найти все живые ссылки при сборке мусора и корректно пройти по стеку при отладке. Именно поэтому рантайм хранит диапазон управляемого кода: получив произвольный адрес, он должен быстро понять, управляемый ли это код и где искать его метаданные.

    Runtime.Base: минимальная CoreLib¶

    Есть курица и яйцо: рантайму нужен System.Object, но полноценная CoreLib слишком сложна для старта. Поэтому существует Runtime.Base - крошечная управляемая библиотека, в которой есть только самое необходимое: Object, String, Array, Exception, RuntimeHelpers, Unsafe.

    Она компилируется прямо в рантайм. Вот как это включается (System.Private.CoreLib.csproj:488):

    Дальше файлы из Runtime.Base просто линкуются в CoreLib как <Compile Include="$(RuntimeBasePath)...">. Поэтому в коде полно #if INPLACE_RUNTIME и #if !INPLACE_RUNTIME: одна и та же логика компилируется по-разному в зависимости от того, встроена она в рантайм или собрана отдельно.

    Мост между управляемым и нативным здесь устроен через два атрибута. RuntimeExport экспортирует управляемый метод наружу под заданным именем (RuntimeExportAttribute.cs:7):

internal sealed class RuntimeExportAttribute : Attribute
{
    public string EntryPoint;
    public RuntimeExportAttribute(string entry) { EntryPoint = entry; }
}

    RuntimeImport делает обратное: объявляет нативную функцию, которую зовет управляемый код. Вместе они дают тот самый мост, по которому ходят аллокации, бокс и исключения.

    Вот пример импорта в управляемом коде (InternalCalls.cs:77):

    [RuntimeImport(RuntimeLibrary, "RhpNewFast")]
[MethodImpl(MethodImplOptions.InternalCall)]
internal static extern unsafe object RhpNewFast(MethodTable* pEEType);

    Здесь RuntimeLibrary - это строка "*", что означает "текущий бинарник". RhpNewFast - имя нативной функции, которую найдет линкер. InternalCall говорит компилятору, что тела у этого метода нет и что вызов надо превратить в нативный. Так управляемый код аллокации попадает в portable.cpp, который мы разберем ниже.

    Отдельно про UnmanagedCallersOnly. Этот атрибут на управляемом методе делает его вызываемым из нативного кода напрямую, без переходного кадра. Синтаксис:

    [UnmanagedCallersOnly(EntryPoint = "MyNativeEntry")]
static int Add(int a, int b) => a + b;

    После компиляции из нативного кода можно объявить extern "C" int MyNativeEntry(int, int) и вызвать. Именно так InitializeModules из StartupCodeHelpers становится доступной нативному main.

    Смотрите, как выглядит бокс (Runtime.Base/src/System/Runtime/RuntimeExports.cs:121):

    Объектная модель¶

    В NativeAOT объект устроен максимально просто. Контракт прописан прямо в комментарии (Runtime.Base/src/System/Object.cs:11):

    // CONTRACT with Runtime
// The Object type is one of the primitives understood by the compilers and runtime
// Data Contract: Single field of type MethodTable*
// VTable Contract: The first vtable slot should be the finalizer for object

    И сам класс (Object.cs:16):

    public unsafe class Object
{
    private MethodTable* m_pEEType;
}

    Все. Указатель на method table и есть объект. Никаких sync block в объекте, как в старом .NET Framework.

    Зачем вообще нужен указатель на method table в каждом объекте. Представьте, что у вас есть переменная типа object, а в ней лежит либо string, либо int, либо ваш класс. Как понять, что это на самом деле, и какие методы можно вызвать. Ответ: посмотреть на первый указатель в объекте. Он ведет на MethodTable, а та уже говорит, что это за тип. Отсюда и растет вся система типов в рантайме: тип объекта определяется его method table, а не тем, что написано в переменной.

    Вот раскладка объекта в памяти. Пусть у нас есть такой класс:

    class Point
{
    public int X;
    public int Y;
}

    Тогда объект Point в куче выглядит так:

    адрес+0:  [alignpad]       4 байта выравнивания
адрес+4:  [sync block]     4 байта заголовка (хэш, блокировка)
адрес+8:  [MethodTable*]   8 байт указателя на тип
адрес+16: [X]              4 байта
адрес+20: [Y]              4 байта

    Почему так. Заголовок 32-битный и лежит вплотную перед указателем на MethodTable. На 64-битной системе перед ним добавляется 4 байта выравнивания, чтобы весь восьмибайтовый блок был выровнен. Вот нативное определение (Runtime/ObjectLayout.h:15):

    class ObjHeader
{
private:
#if defined(HOST_64BIT)
    uint32_t   m_uAlignpad;
#endif // HOST_64BIT
    uint32_t   m_uSyncBlockValue;
    ...
};

    Именно m_uAlignpad и есть те самые 4 байта пустоты. А m_uSyncBlockValue - это sync block в комментарии GetHeaderPtr, который читается как (int*)ppMethodTable - 1, то есть за 4 байта до указателя. Компилятор знает весь расклад и генерирует обращения к полям по смещениям: X - это адрес+16, Y - адрес+20.

    Теперь про vtable. Это массив указателей на методы, который лежит сразу за заголовком MethodTable. Когда вы пишете виртуальный вызов:

    Shape s = new Circle();
double a = s.Area();

    Компилятор превращает это примерно в такой код на псевдо-C++:

    // s - это указатель на объект
MethodTable* mt = *(MethodTable**)s;          // взять method table из объекта
void** vtable = mt->GetVtable();              // vtable лежит сразу за заголовком
double (*area)(void*) = vtable[AreaSlot];     // взять метод по слоту
double a = area(s);                           // вызвать

    Индекс слота AreaSlot компилятор знает заранее: он одинаков для всех типов, реализующих Area. Именно поэтому один и тот же вызов работает для любого наследника. А девиртуализация, о которой мы говорили выше, заменяет этот танец на прямой Circle.Area(s), когда компилятор доказал, что других вариантов нет.

    Перед этим указателем, в памяти, лежит заголовок. Он описан так (Common/src/Internal/Runtime/MethodTable.cs:15):

    [StructLayout(LayoutKind.Sequential)]
internal struct ObjHeader
{
    // Contents of the object header
    private IntPtr _objHeaderContents;
}

    Заголовок расположен ровно за 4 байта до указателя на method table (ObjectHeader.NativeAot.cs:49):

    private static unsafe int* GetHeaderPtr(MethodTable** ppMethodTable)
{
    // The header is 4 bytes before m_pEEType field on all architectures
    return (int*)ppMethodTable - 1;
}

    В этих 4 байтах живут хэш-код объекта, тонкая блокировка (thin lock) и индекс записи в sync-таблице (ObjectHeader.NativeAot.cs:21):

    //   BIT_SBLK_UNUSED        = 0x80000000
//   BIT_SBLK_FINALIZER_RUN = 0x40000000
//   BIT_SBLK_GC_RESERVE    = 0x20000000

    Разберем, что это значит. Хэш-код - значение, которое возвращает GetHashCode(). Его невыгодно хранить в каждом объекте, потому что большинство объектов в хэш-таблицы не попадают. Поэтому он вычисляется лениво и кладется в заголовок только при первом обращении.

    Thin lock (тонкая блокировка) - оптимизация для lock. Когда поток входит в lock(obj), вместо создания полноценного объекта-мьютекса его идентификатор записывается прямо в заголовок объекта. Если объект никто не конкурирует, это одна атомарная операция вместо системного вызова. Только при реальной конкуренции создается "толстая" блокировка в sync-таблице - отдельном массиве, где на каждый спорный объект есть запись.

    Комментарий в исходнике объясняет порог (ObjectHeader.NativeAot.cs:254):

    // If we see a thin lock held by other thread for longer than ~5 microseconds, we will "inflate" the lock
// and let the adaptive spinning in the fat Lock sort it out whether we have a contentious lock or a long-held lock.

    Идея в том, что тонкая блокировка хороша для коротких некотенциозных критических секций. Если ее держат долго, выгоднее "раздуть" ее в полноценный объект и отдать решение операционной системе.

    Итого раскладка объекта: [ObjHeader 4 байта][padding 4 байта][MethodTable* 8 байт][поля...]. Именно поэтому GetRawDataSize вычитает оба заголовка (Object.cs:67):

    internal uint GetRawDataSize()
{
    return m_pEEType->BaseSize - (uint)sizeof(ObjHeader) - (uint)sizeof(MethodTable*);
}

    Сам MethodTable - это структура с фиксированным заголовком и vtable'ом следом (MethodTable.cs:169):

    private uint _uFlags;
private uint _uBaseSize;
private RelatedTypeUnion _relatedType;
private ushort _usNumVtableSlots;
private ushort _usNumInterfaces;
private uint _uHashCode;

// vtable follows

    _uFlags хранит флаги типа, а младшие биты - размер элемента для массивов и строк либо количество generic-параметров. _relatedType - это union: для обычного типа там базовый тип, для массива - тип элемента (MethodTable.cs:137). _uBaseSize - размер объекта, который так важен для аллокации.

    Проясним каждый элемент, потому что здесь легко запутаться.

    _uFlags - это одно 32-битное слово, в котором упаковано много всего. Старшие 16 бит - флаги: является ли тип интерфейсом, содержит ли ссылки, финализируемый ли он, и так далее. Младшие 16 бит переиспользуются под разные нужды в зависимости от типа: для массива и строки это размер одного элемента (чтобы посчитать размер массива из длины), для generic-типа - число параметров. Это экономия памяти: не заводить отдельные поля, если их можно совместить.

    _uBaseSize - базовый размер объекта в байтах. Именно его читает RhpNewFast, чтобы сдвинуть указатель аллокации. Для Point из примера выше это 24 байта: 8 на заголовок с указателем и 8 на два int с выравниванием.

    _relatedType - это union, то есть объединение, где все поля лежат по одному адресу и занимают одну память. Вот его определение (MethodTable.cs:137):

    [StructLayout(LayoutKind.Explicit)]
private unsafe struct RelatedTypeUnion
{
    // Kinds.CanonicalEEType
    [FieldOffset(0)]
    public MethodTable* _pBaseType;

    // Kinds.ArrayEEType
    [FieldOffset(0)]
    public MethodTable* _pRelatedParameterType;
}

    [FieldOffset(0)] у обоих полей означает "положи по смещению 0". Значит, это одна и та же память, просто два имени. Для обычного класса здесь базовый тип: Circle ссылается на Shape. Для массива здесь тип элемента: int[] ссылается на int. Читать надо правильное поле в зависимости от того, массив это или нет. Это классический прием из мира C, где память экономят ценой внимательности программиста.

    _usNumVtableSlots и _usNumInterfaces - сколько слотов в vtable и сколько интерфейсов реализует тип. По ним рантайм знает размеры массивов, которые идут следом за заголовком.

    Аллокация¶

    Быстрый путь аллокации - это тот самый bump pointer. Вот он в Runtime/portable.cpp:57:

    FCIMPL1(Object *, RhpNewFast, MethodTable* pEEType)
{
    ASSERT(!pEEType->HasFinalizer());

    Thread * pCurThread = ThreadStore::GetCurrentThread();
    gc_alloc_context * acontext = pCurThread->GetAllocContext();
    size_t size = pEEType->GetBaseSize();

    uint8_t* alloc_ptr = acontext->alloc_ptr;
    uint8_t* combined_limit = pCurThread->GetEEAllocContext()->GetCombinedLimit();
    if ((size_t)(combined_limit - alloc_ptr) >= size)
    {
        acontext->alloc_ptr = alloc_ptr + size;
        Object* pObject = (Object *)alloc_ptr;
        pObject->SetMethodTable(pEEType);
        return pObject;
    }

    return AllocateObject(pEEType, 0, 0);
}

    Ничего нового после урока про GC: сдвинули указатель, записали method table, вернули объект. Отличие в combined_limit. Это предел, до которого можно аллоцировать, не заботясь о сэмплировании аллокаций для профилировщика. Если включено сэмплирование, combined_limit может быть меньше реального alloc_limit, и пересечение сэмплированной точки уводит на медленный путь.

    Разберем по шагам, что делает этот код, на примере выделения Point размером 24 байта.

    Пусть у потока сейчас такое состояние аллокационного контекста:

    alloc_ptr   = 0x1000   // следующий свободный байт
alloc_limit = 0x2000   // конец текущего куска

    Шаги:

    1. size = pEEType->GetBaseSize() дает 24.
    2. alloc_ptr = 0x1000, combined_limit = 0x2000.
    3. Проверяем 0x2000 - 0x1000 = 0x1000 >= 24 - да, места хватает.
    4. acontext->alloc_ptr = 0x1000 + 24 = 0x1018 - сдвинули указатель.
    5. pObject = 0x1000, пишем туда указатель на MethodTable.
    6. Возвращаем 0x1000.

    Все. Никаких поисков свободного блока, никакой блокировки: каждый поток работает со своим контекстом. Отсюда и скорость.

    Схематично:

    до:    [занято........][ free ......................]
         ^              ^                          ^
       начало         alloc_ptr                  alloc_limit

после: [занято........][Point][ free ...............]
                       ^       ^                   ^
                     вернули  alloc_ptr          alloc_limit

    Что такое сэмплирование аллокаций. Профилировщику не нужно видеть каждую аллокацию: он выбирает случайные точки в потоке аллокаций и записывает, что там было выделено. Это дешевле, чем логировать все подряд. Точка, которую надо засэмплировать, может попасть внутрь текущего куска. Тогда combined_limit ставится раньше alloc_limit, чтобы объект, накрывающий эту точку, ушел на медленный путь и был залогирован. Если сэмплирование выключено, combined_limit всегда равен alloc_limit, и проверка становится тривиальной.

    Медленный путь AllocateObject заканчивается вызовом GC (Runtime/GCHelpers.cpp:611):

    Object* pObject = GCHeapUtilities::GetGCHeap()->Alloc(pAllocContext, cbSize, uFlags);

    То есть NativeAOT использует тот же самый сборщик из src/coreclr/gc, что и CoreCLR. Никакого отдельного GC тут нет. В GCHelpers.cpp есть даже проверка, что аллокационный квант не больше порога больших объектов (GCHelpers.cpp:641):

    ASSERT(acontext->alloc_limit - acontext->alloc_ptr <= RH_LARGE_OBJECT_SIZE);

    Запуск управляемого кода¶

    После того как нативный main вызвал RhInitialize и InitializeModules, управление уходит в __managed__Main. Но перед Main нужно подготовить модули. Это делает StartupCodeHelpers.InitializeModules (Common/.../StartupCodeHelpers.cs:30):

    ...

        RunInitializers(modules[i], ReadyToRunSectionType.EagerCctor);
}

    Обратите внимание на комментарий (StartupCodeHelpers.cs:49):

// the first class constructor to prevent them calling into another uninitialized module

    Сначала все модули регистрируются и получают таблицы статики, и только потом запускаются eager-конструкторы. Иначе первый же конструктор мог бы обратиться к еще не созданным данным соседнего модуля.

    Ленивые статические конструкторы запускаются позже, при первом обращении к типу, через ClassConstructorRunner.

    Разберем, что такое статический конструктор и почему с ним столько возни. Статический конструктор - это блок, который выполняется один раз, перед первым использованием типа:

    class Config
{
    public static readonly string Path;

    static Config()
    {
        Path = Environment.GetEnvironmentVariable("APP_PATH") ?? "default";
    }
}

    В обычном .NET гарантируется, что этот код выполнится ровно один раз и до того, как к Path впервые обратятся, причем потокобезопасно. Это значит, что рантайм должен отслеживать состояние каждого типа: "конструктор еще не запускался", "выполняется прямо сейчас другим потоком", "уже выполнен".

    Eager (нетерпеливые) конструкторы выполняются сразу при старте, для всех типов, которые компилятор пометил как нужные. Это те самые RunInitializers(..., ReadyToRunSectionType.EagerCctor). Плюс: к моменту Main все готово, никаких проверок в горячем пути. Минус: старт дольше, потому что делается работа, которая могла бы не понадобиться.

    Lazy (ленивые) конструкторы выполняются при первом обращении. Плюс: старт быстрее. Минус: на каждом обращении к статике нужна проверка состояния и, при необходимости, ожидание. Компилятор решает, какие конструкторы можно сделать eager, а какие нельзя (например, если они зависят от данных, доступных только в рантайме).

    Метаданные и рефлексия¶

    Тримминг выбросил все, что не используется. Значит, рефлексия по умолчанию почти ничего не найдет. Есть несколько уровней:

    • --reflectiondata:none - рефлексии нет вообще, самый маленький бинарник.
    • --reflectiondata:all - сгенерировать метаданные для всего, что осталось.
    • --completetypemetadata - полные метаданные типов.

    Управляется это в Program.Run (Program.cs:116):

    bool supportsReflection = reflectionData != "none" && systemModuleName == Helpers.DefaultSystemModule;

    Покажем проблему на примере. Пусть есть такой код:

    string name = "MyApp.Models.Order";
Type t = Type.GetType(name);
object instance = Activator.CreateInstance(t);

    Компилятор смотрит на этот код и не может доказать, какой именно тип имеется в виду: строка name собирается в рантайме. Если тип MyApp.Models.Order больше нигде не упоминается явно, граф зависимостей до него не дотянется, и тримминг его выбросит. В рантайме Type.GetType вернет null, и код упадет.

    Решения два. Либо перечислить тип в rd.xml, чтобы он попал в корни. Либо пометить в коде, что он нужен:

    [DynamicallyAccessedMembers(DynamicallyAccessedMemberTypes.All)]
static void Create(string name) { ... }

    Атрибут DynamicallyAccessedMembers говорит компилятору: "этот метод может использовать рефлексию, не вырезай то, к чему он может обратиться". Компилятор проверит, что вы не передаете сюда произвольную строку из воздуха, и выдаст предупреждение, если не может гарантировать безопасность.

    Если рефлексия не поддерживается, ставится FullyBlockedMetadataBlockingPolicy (Program.cs:449), и любая попытка рефлексии ведет к ошибке, а не к тихому null. Это лучше, чем узнать в продакшене, что тип был вырезан.

    Типы, которые нужны только через рефлексию, приходится перечислять в rd.xml. Синтаксис описан в nativeaot/docs/rd-xml-format.md.

    Interop¶

    Экспорт управляемого метода в нативный мир делается атрибутом UnmanagedCallersOnly с именем точки входа. Внутри самой библиотеки тот же механизм через RuntimeExport. Импорт нативных функций - LibraryImport или DllImport, которые ILC превращает в прямые вызовы.

    Пример экспорта управляемого кода наружу:

    using System.Runtime.InteropServices;

public static class NativeApi
{
    [UnmanagedCallersOnly(EntryPoint = "sum_array")]
    public static unsafe double SumArray(double* data, int length)
    {
        double sum = 0;
        for (int i = 0; i < length; i++)
            sum += data[i];
        return sum;
    }
}

    После dotnet publish этот метод можно вызвать из C++:

    extern "C" double sum_array(double* data, int length);

    Обратите внимание: метод статический, параметры только blittable-типов, никаких исключений наружу. Все потому, что нативная сторона не умеет разбирать управляемые объекты и исключения. Это не ограничение NativeAOT, а фундаментальная граница между двумя мирами.

    Пример импорта нативной функции в управляемый код:

    using System.Runtime.InteropServices;

public static partial class Native
{
    [LibraryImport("mylib", EntryPoint = "native_compute")]
    internal static partial double Compute(double x, int mode);
}

    LibraryImport - это современный генераторный вариант DllImport. На этапе компиляции он создает код маршалинга, который ILC затем оптимизирует. Для простых blittable-типов маршалинга не будет вообще: вызов превратится в прямой переход в нативную функцию. Для string или массивов появится код конвертации, и это место, где легко случайно начать аллоцировать.

    Из интересного на уровне сборки: статическая линковка ICU и OpenSSL (nativeaot/docs/compiling.md:68), чтобы бинарник не зависел от системных библиотек, и кросс-архитектурная компиляция. Важная деталь (compiling.md:38):

    Native AOT toolchain allows targeting ARM64 on an x64 host and vice versa for both Windows and Linux.
Cross-OS compilation, such as targeting Linux on a Windows host, is not supported.

    То есть собрать ARM64 на x64 можно, а Linux на Windows нельзя. Это прямое следствие того, что для линковки нужен нативный тулчейн целевой платформы.

    Что покрутить в проекте¶

    Минимум для включения:

    <PropertyGroup>
  <PublishAot>true</PublishAot>
</PropertyGroup>

    Что происходит при dotnet publish с этой настройкой. SDK видит PublishAot и вместо обычной публикации с runtimeconfig.json и DLL-ками запускает ILC. Тот компилирует всю программу в объектные файлы, а нативный тулчейн линкует их с рантаймом. На выходе в publish лежит один исполняемый файл, например MyApp.exe на Windows или MyApp на Linux, плюс, возможно, файл отладочных символов (MyApp.pdb или MyApp.dbg). Ни dotnet в PATH, ни установленного рантайма для запуска не нужно.

    Полезные свойства (nativeaot/docs/optimizing.md):

    • <IlcInstructionSet>avx2,bmi2,fma,pclmul,popcnt,aes</IlcInstructionSet> - разрешить инструкции новее базовых. native под текущий CPU.
    • <IlcMaxVectorTBitWidth>256</IlcMaxVectorTBitWidth> - ограничить размер Vector<T>, чтобы бинарник не требовал AVX512 там, где не нужно.
    • <IlcGenerateMapFile>true</IlcGenerateMapFile> - карта того, что попало в бинарник. Без нее непонятно, почему он такой большой.
    • <IlcGenerateMstatFile>true</IlcGenerateMstatFile> - статистика по типам и методам.
    • <IlcGenerateDgmlFile>true</IlcGenerateDgmlFile> - граф зависимостей, открывается в VS.

    Отдельно про размер: IlcGenerateCompleteTypeMetadata и высокий уровень рефлексии заметно раздувают бинарник. Если рефлексия нужна только для пары типов, дешевле перечислить их точечно.

    Как заглянуть внутрь бинарника¶

    Когда бинарник весит 40 МБ, хочется понять, что там. Включаем карту и статистику:

    <PropertyGroup>
  <IlcGenerateMapFile>true</IlcGenerateMapFile>
  <IlcGenerateMstatFile>true</IlcGenerateMstatFile>
</PropertyGroup>

    После публикации рядом появятся MyApp.map и MyApp.mstat. В map-файле видно, какие методы и типы попали в бинарник и сколько каждый весит. В mstat - сводка по категориям. Типичный сценарий: видите в mstat, что половину занимают метаданные рефлексии, и отключаете IlcGenerateCompleteTypeMetadata, если рефлексия не нужна.

    Граф зависимостей можно открыть в Visual Studio:

    <IlcGenerateDgmlFile>true</IlcGenerateDgmlFile>

    Получится MyApp.dgml, в котором узлы - типы и методы, а ребра - зависимости. Очень помогает, когда непонятно, почему в бинарник затянулся целый пласт кода: ищешь путь от корня до подозрительного узла и находишь виновника.

    Еще можно управлять объемом метаданных. По умолчанию ILC тримит их, оставляя только то, что достижимо. Если рефлексия не нужна совсем, не включайте полные метаданные:

    <!-- по умолчанию true: метаданные тримятся -->
<IlcTrimMetadata>true</IlcTrimMetadata>

    Если же выставить <IlcTrimMetadata>false</IlcTrimMetadata>, ILC передаст компилятору --reflectiondata:all (Microsoft.NETCore.Native.targets:315), и в бинарник попадут метаданные для всего, что осталось после тримминга кода. Это резко увеличивает размер, зато рефлексия начинает находить типы. Включайте осознанно и только там, где она реально нужна.

    Ловушки¶

    Нет загрузки новых сборок в рантайме. Все, что не попало в бинарник при сборке, недоступно. Assembly.LoadFrom в привычном виде не работает.

    Это прямое следствие AOT: код уже скомпилирован и лежит в бинарнике, загрузить что-то новое неоткуда. Плагинная архитектура с внешними DLL в привычном виде не собирается. Вместо этого плагины компилируются в тот же бинарник и выбираются по имени типа, либо используется нативный interop.

    Reflection.Emit не работает. Кодогенерации в рантайме нет. Если библиотека строит типы на лету, она несовместима с NativeAOT.

    Reflection.Emit - это API, который позволяет создать новый тип прямо во время выполнения и сгенерировать для него код. Это возможно только когда есть JIT. Типичные жертвы: сериализаторы, генерирующие код на ходу, некоторые ORM и прокси-библиотеки. Ищите source generators или AOT-совместимые альтернативы.

    Тримминг ломает рефлексию. Компилятор предупреждает о местах, где рефлексия может не найти тип, но не всегда может доказать проблему. [DynamicallyAccessedMembers] и rd.xml - ваши инструменты.

    Практическое правило: включайте предупреждения об AOT как ошибки в CI (<TrimmerSingleWarn>false</TrimmerSingleWarn>, TreatWarningsAsErrors), чтобы проблема всплыла на сборке, а не у пользователя. И покрывайте рефлексивные пути тестами именно в AOT-сборке, потому что обычный dotnet test их не поймает.

    Vector<T> фиксируется на этапе сборки. JIT мог бы подстроиться под конкретный CPU, а ILC решает заранее. Отсюда IlcMaxVectorTBitWidth и требование инструкций в IlcInstructionSet.

    Vector<T> - это тип, который использует SIMD-инструкции процессора. Его размер (128, 256, 512 бит) зависит от того, какие инструкции доступны. JIT определяет это при запуске, а ILC обязан выбрать размер при сборке, потому что иначе нельзя сгенерировать код. Компромисс: собирайте под базовый набор для переносимости или под AVX2/AVX512 для скорости, но тогда бинарник не запустится на старом железе.

    CPU без нужных инструкций не запустится. Это проверка в DetectCPUFeatures, и это осознанный размен: скорость против переносимости.

    Если нужна максимальная совместимость, не указывайте IlcInstructionSet вообще: тогда ILC целится в минимальный набор целевой платформы. Если нужна скорость и вы контролируете парк машин, указывайте конкретный набор и документируйте требования.

    Стабильная скорость, но не всегда лучшая. Нет tiered compilation и динамического PGO, поэтому пиковая производительность горячего цикла может быть ниже, чем у CoreCLR с динамической профилировкой. Зато нет пауз на JIT и предсказуемый старт.

    Tiered compilation в CoreCLR сначала компилирует метод быстро и неоптимально, а потом, если метод оказался горячим, перекомпилирует его с оптимизациями. PGO использует профиль реального выполнения, чтобы лучше расположить ветки и инлайны. ILC ничего этого в рантайме сделать не может. Частично это компенсируется статическим анализом и MBIC-профилями, но не полностью.

    EH и stack walking устроены иначе. Рантайм разбирает стек через StackFrameIterator и диапазон управляемого кода. Если вы делаете глубокий interop с нативным кодом и полагаетесь на точный stack trace через границы, проверяйте поведение отдельно.

    EH (exception handling) - обработка исключений. В NativeAOT раскрутка стека завязана на GC info и диапазоны кода, которые компилятор сгенерировал для каждого метода. Через нативные границы точность может теряться: кадры нативного кода не всегда попадают в управляемый stack trace. Для диагностики управляйте данными трассировки: <StackTraceSupport>true</StackTraceSupport> (по умолчанию включено) добавляет имена методов, а <StackTraceLineNumberSupport>true</StackTraceLineNumberSupport> еще и номера строк, но заметно раздувает бинарник. Проверяйте, что нужные кадры на месте, именно в AOT-сборке.

    Что в итоге¶

    NativeAOT - это компилятор ILC, который видит всю программу целиком и генерирует нативный код через тот же RyuJIT, плюс нативный рантайм, который переиспользует GC из CoreCLR. Управляемый код и рантайм сцеплены через таблицу classlib-функций и bookend-секции, которые линкер склеивает в единые диапазоны. Объект - это ObjHeader плюс указатель на MethodTable, а аллокация - все тот же сдвиг указателя в per-thread контексте.

    Цена всего этого - отказ от динамической загрузки и рантайм-кодогенерации, фиксация набора инструкций и обязательный тримминг. Взамен - один бинарник, быстрый старт и отсутствие JIT. Для CLI-утилит, сервисов и нативных библиотек это почти всегда выигрыш. Для приложений, которые живут рефлексией и плагинами, - почти всегда боль.
