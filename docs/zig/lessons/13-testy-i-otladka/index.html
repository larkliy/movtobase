    13. Тесты и отладка¶

    Зачем это нужно и в чем прикол¶

    Zig проверяет типы, безопасность и многие ошибки на этапе компиляции. Но он не знает, что ваша функция считает налог неправильно или что парсер падает на пустом файле. Для этого нужны тесты.

    Тесты в Zig - часть языка, а не отдельный фреймворк. Блок test компилируется только в тестовую сборку, может лежать рядом с кодом и имеет доступ к приватным функциям. std.testing дает проверки, а тестовый аллокатор ловит утечки. zig build test запускает все тесты проекта.

    Отладка тоже встроена: std.debug.print, @breakpoint, трейсы, std.debug.dumpStackTrace. В 0.17 к этому добавился новый I/O, но базовые инструменты прежние.

    Базовый синтаксис¶

    const std = @import("std");
const testing = std.testing;

fn sum(xs: []const i32) i32 {
    var total: i32 = 0;
    for (xs) |x| total += x;
    return total;
}

test "sum" {
    try testing.expectEqual(@as(i32, 6), sum(&.{ 1, 2, 3 }));
    try testing.expectEqual(@as(i32, 0), sum(&.{}));
}

test "expectError" {
    try testing.expectError(error.OutOfMemory, fail());
}

fn fail() error{OutOfMemory}!void {
    return error.OutOfMemory;
}

    Что используется:

    • test "name" { ... } - тестовый блок. Имя произвольное, нужно для вывода и фильтрации.
    • std.testing.expect(condition) - проверка истинности.
    • expectEqual(expected, actual) - проверка равенства. Типы должны совпадать; поэтому @as(i32, 6), а не просто 6 (иначе будет comptime_int).
    • expectEqualStrings(expected, actual) - для строк.
    • expectError(error.X, expression) - проверка ошибки.
    • expectFmt(expected, format, args) - проверка форматирования.
    • try перед проверкой: проверки возвращают !void, тест тоже может вернуть ошибку.

    Запуск:

    zig test src/main.zig
zig test src/main.zig --test-filter sum
zig build test

    --test-filter запускает только тесты, в имени которых есть подстрока.

    Тестовый аллокатор и утечки¶

    test "no leaks" {
    var list: std.ArrayList(u8) = .empty;
    defer list.deinit(testing.allocator);

    try list.appendSlice(testing.allocator, "hello");
    try testing.expectEqualStrings("hello", list.items);
}

    std.testing.allocator - специальный аллокатор, который в конце теста проверяет, что вся выделенная память освобождена. Если забыть deinit, тест упадет с отчетом об утечке.

    Для проверки обработки OutOfMemory есть std.testing.checkAllAllocationFailures:

    test "allocation failures" {
    try testing.checkAllAllocationFailures(testing.allocator, testFn, .{});
}

fn testFn(allocator: std.mem.Allocator) !void {
    var list: std.ArrayList(u8) = .empty;
    defer list.deinit(allocator);
    try list.appendSlice(allocator, "hello");
}

    Он запускает функцию много раз, каждый раз «ломая» выделение на очередном шаге, и проверяет, что код корректно откатывается.

    Тесты в build.zig¶

    const tests = b.addTest(.{ .root_module = mathx });
const run_tests = b.addRunArtifact(tests);
const test_step = b.step("test", "Run tests");
test_step.dependOn(&run_tests.step);

    addTest создает тестовый исполняемый файл из модуля. addRunArtifact запускает его. b.step("test", ...) делает шаг доступным как zig build test.

    Отладка¶

    std.debug.print("value={d}\n", .{value});

    std.debug.print пишет в stderr и не требует аллокатора. В 0.17 он использует буфер и новый I/O, но синтаксис остался удобным.

    Для точки останова:

    @breakpoint();

    При запуске под отладчиком (VS Code + CodeLLDB, gdb, lldb) выполнение остановится в этом месте. Без отладчика @breakpoint может привести к trap.

    Для трейса:

    std.debug.dumpStackTrace(@errorReturnTrace().?);

    Это полезно, когда ошибка обработана, но непонятно, откуда она пришла. В release-режиме трейсы могут быть отключены.

    Смотрим в сурсы: что там под капотом¶

    std.testing лежит в lib/std/testing.zig. Основные функции - тонкие обертки над std.debug и сравнением:

    pub fn expect(ok: bool) error{TestExpectedEqual}!void
pub fn expectEqual(expected: anytype, actual: anytype) !void
pub fn expectEqualStrings(expected: []const u8, actual: []const u8) !void
pub fn expectError(expected_error: anyerror, actual_error_union: anytype) !void

    Тестовый аллокатор - это std.testing.allocator, обертка над DebugAllocator с включенной проверкой утечек. Поэтому тесты и defer так хорошо сочетаются: аллокатор сам скажет, что вы забыли освободить.

    b.addTest в lib/std/Build.zig создает Step.Compile с kind = .test. Тестовый бинарник содержит сгенерированный test runner, который вызывает все блоки test в корневом модуле и его импортах. Поэтому тесты не нужно регистрировать вручную - достаточно, чтобы файл был доступен из корневого модуля.

    Где можно споткнуться¶

    1. expectEqual требует одинаковый тип. expectEqual(6, sum(...)) может не собраться, если sum возвращает i32, а 6 - comptime_int. Пишите @as(i32, 6) или try testing.expectEqual(@as(i32, 6), actual).

    2. Тесты не запускаются сами. zig build не запускает тесты, если вы не добавили шаг test и не вызвали zig build test. В CI это нужно делать явно.

    3. Тестовый аллокатор ловит только явные утечки. Память, выделенная через page_allocator или C malloc, вне его контроля. Для тестов используйте testing.allocator и передавайте его в код.

    4. defer срабатывает и при ошибке. Это удобно, но порядок defer - обратный порядку объявления. Если ресурсы зависят друг от друга, следите за порядком.

    5. @breakpoint не работает без отладчика. В обычном запуске это trap, а не «пауза». Для логирования используйте std.debug.print.

    6. Не тестируйте все подряд. Тесты должны проверять контракты и граничные случаи, а не повторять реализацию. Начните с public API и ошибок.

    7. test-блоки в импортируемых модулях. Они компилируются, только если модуль входит в тестовую сборку. Если тест лежит в отдельном файле, добавьте его в addTest или импортируйте из корневого файла.

    8. Тесты и ReleaseFast. В release-режиме проверки безопасности отключены, поэтому тесты, которые полагаются на панику, могут вести себя иначе. Запускайте тесты в Debug и, при необходимости, в ReleaseSafe.
