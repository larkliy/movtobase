Классический парсинг строк в .NET долгие годы был источником бесконечных аллокаций. Стоило взять входящую строку на пару килобайт и разбить её по разделителю с помощью `string.Split` или вырезать подстроки через `Substring`, как куча немедленно наполнялась сотнями мелких объектов `string`. В высоконагруженном сетевом сервисе эти короткоживущие строки забивали Gen 0 за секунды, провоцируя частые сборки мусора и непредсказуемые скачки p99 latency.

Причина проста: `string` в C# иммутабелен и всегда живёт в управляемой куче. Любая операция `Substring` физически аллоцирует новый объект строки и копирует в него символы из исходного буфера.

Появление `Span<T>` и `Memory<T>` в C# 7.2 и .NET Core 2.1 фундаментально изменило подход к работе с памятью. Вместо создания новых копий данных мы получили возможность работать с окнами (срезами) произвольной непрерывной памяти без единого байта аллокаций в куче.

## Анатомия ref struct: почему Span<T> быстрее обычных объектов

Взглянем на определение `Span<T>` в базовой библиотеке рантайма `src/libraries/System.Private.CoreLib/src/System/Span.cs`:

![Анатомия ref struct Span<T>](/movtobase/images/csharp/code-span-struct-def.svg)

Структура содержит всего два поля:
1. `internal readonly ref T _reference` — управляемая ссылка (managed byref / interior pointer).
2. `private readonly int _length` — число доступных элементов.

На 64-битной платформе `Span<T>` занимает в памяти ровно **16 байт** (8 байт на указатель + 4 байта длины + 4 байта выравнивания). Он передаётся через регистры процессора или локальный стек потока.

Сравним организацию памяти обычного массива в куче и стекового среза:

![Анатомия памяти: Span vs Managed Object](/movtobase/images/csharp/span-memory-layout.svg)

У любого объекта в управляемой куче есть фиксированный оверхед:
- **SyncBlock Index** (8 байт на x64) — служебный заголовок для блокировок `lock`, хэш-кодов и статусов GC.
- **MethodTable Pointer** (8 байт на x64) — указатель на таблицу методов и метаданные типа.
- **Поле длины** (для массивов и строк).

У `Span<T>` заголовка кучи нет вообще. Он не является объектом в понимании CoreCLR и не требует регистрации в структурах аллокатора.

Строение стека вызовов и локальных ссылочных переменных задокументировано в BOTR:

![Стек вызовов CoreCLR и размещение фреймов (BOTR)](/movtobase/images/csharp/stack.png)

Поскольку `Span<T>` объявлен со спецификатором `ref struct`, компилятор C# (Roslyn) и верификатор рантайма накладывают на него строжайшие правила времени жизни:
- **Нельзя упаковать в `object` (boxing).** Вызов `((object)span)` или передача в интерфейс запрещены на уровне компиляции.
- **Нельзя разместить в полях обычного класса или обычной структуры.** Иначе структура могла бы утечь в кучу.
- **Нельзя использовать в качестве обобщённого параметра** в стандартных дженериках (до появления фичи `allows ref struct` в C# 13).
- **Нельзя захватывать в лямбды** и использовать внутри `async/await` методов через точки ожидания.

## Interior Pointer: как GC не теряет адрес внутри массива

Что делает управляемая ссылка `ref T _reference` особенной? Это так называемый **внутренний указатель (interior pointer)**.

Обычный объектный указатель (`object`) всегда указывает строго на нулевой байт объекта в куче (на поле `MethodTable`):

![Схема размещения MethodTable и полей объекта (BOTR)](/movtobase/images/csharp/typeloader-fig1.png)

Внутренний указатель `ref T` может указывать в любую точку внутри тела объекта: на десятый элемент массива, на внутреннее поле структуры или даже на байт посреди буфера. 

Если в момент работы вашего кода запустится компактирующая сборка мусора (Compact Phase) и сборщик решит сдвинуть базовый массив в памяти на 512 байт влево, GC автоматически обновит значение `_reference` внутри вашего стекового `Span<T>`, прибавив к нему то же самое смещение!

Рантайм умеет это делать, потому что JIT-компилятор сохраняет информацию о типе каждой стековой ячейки в GC-карте метода. Сборщик видит, что слот содержит `byref`, находит родительский объект в таблице регионов и деликатно корректирует адрес.

## Единый фасад для трёх видов памяти

Ключевая мощь `Span<T>` в том, что один и тот же алгоритм может работать с памятью из совершенно разных источников:

```csharp
// 1. Управляемый массив в куче
byte[] heapArray = new byte[1024];
Span<byte> span1 = heapArray.AsSpan();

// 2. Локальный буфер на стеке (stackalloc) — 0 аллокаций, мгновенное освобождение
Span<byte> span2 = stackalloc byte[256];

// 3. Неуправляемая память из native malloc / mmap
IntPtr nativePtr = Marshal.AllocHGlobal(512);
try
{
    unsafe
    {
        Span<byte> span3 = new Span<byte>((void*)nativePtr, 512);
        // парсим данные одинаково для всех трёх вариантов!
        ParseProtocol(span3);
    }
}
finally
{
    Marshal.FreeHGlobal(nativePtr);
}
```

Методу `ParseProtocol(Span<byte> data)` абсолютно всё равно, где физически расположены байты — на стеке текущего потока, в управляемой куче или в видеопамяти драйвера.

## Bounds Check Elimination: почему Span быстрый в циклах

Каждое обращение `span[i]` формально содержит проверку выхода за границы (`index < _length`). В наивном коде это приводило бы к лишним ветвлениям и замедлению.

Однако RyuJIT умеет выполнять оптимизацию **Bounds Check Elimination (BCE)**. Если компилятор видит стандартный цикл:

```csharp
public static int Sum(ReadOnlySpan<int> values)
{
    int total = 0;
    for (int i = 0; i < values.Length; i++)
    {
        total += values[i]; // JIT доказывает, что i всегда < values.Length, и удаляет cmp
    }
    return total;
}
```

JIT на этапе SSA-анализа доказывает инвариант цикла и полностью вырезает инструкции проверки диапазона из машинного кода. Более того, для операций над простыми типами RyuJIT автоматически применяет автовекторизацию (SIMD), разворачивая итерации с использованием инструкций AVX2 / AVX-512.

## Проблема асинхронности: почему одного Span<T> недостаточно

Всё прекрасно, пока мы находимся в синхронном коде. Но что происходит, когда в дело вступает асинхронность (`async/await`)?

Вспомним, как устроен `async`: когда метод доходит до точки `await socket.ReadAsync()`, выполнение синхронно возвращается вызывающему коду, а текущий фрейм метода упаковывается в сгенерированную компилятором структуру машины состояний (State Machine Box). Эта машина состояний аллоцируется **в управляемой куче**.

А `ref struct` запрещено помещать в кучу! Компилятор C# выдаст ошибку `CS4013: Cannot use type 'Span<byte>' across an await expression`.

Именно для этой цели существует парный тип: `Memory<T>` / `ReadOnlyMemory<T>`.

Заглянем в `src/libraries/System.Private.CoreLib/src/System/Memory.cs`:

![Структура Memory<T> для async-контекстов](/movtobase/images/csharp/code-memory-struct-def.svg)

В отличие от `Span<T>`, `Memory<T>` — это **обычная структура** (`struct`), а не `ref struct`. Она спокойно пересекает границы `await`, может храниться в полях классов и передаваться в таски.

Она хранит:
- `_object` — ссылку на несущий объект в куче (`string`, `T[]` или специальный `MemoryManager<T>`).
- `_index` — смещение начала диапазона.
- `_length` — длину окна.

Когда вам нужно непосредственно прочитать или записать байты в синхронном блоке, вы вызываете свойство `memory.Span`, получая легковесный `Span<T>` прямо на локальном стеке.

## MemoryManager<T>: оборачиваем кастомную память в Memory<T>

Что делать, если у вас есть пул нативной памяти, память с дискового маппинга (`MemoryMappedFile`) или буферы из аппаратно-закреплённого пула, но вы хотите отдавать их в асинхронные методы в виде `Memory<T>`?

Для этого рантайм предоставляет абстрактный класс `MemoryManager<T>` (`src/libraries/System.Private.CoreLib/src/System/Buffers/MemoryManager.cs`):

![Базовый класс MemoryManager<T>](/movtobase/images/csharp/code-memory-manager.svg)

Реализовав три метода — `GetSpan()`, `Pin()` и `Unpin()`, вы получаете полноценный объект-владелец. Вызов `manager.Memory` даёт валидный экземпляр `Memory<T>`, который можно безопасно передавать в любые стандартные API .NET, включая Kestrel, `System.IO.Pipelines` и `HttpClient`.

## Практический пример: безаллокационный парсер чисел

Посмотрим на разницу между старым подходом и современным кодом на срезах. Допустим, мы парсим CSV-строку с метриками: `"sensor_42;189.55;true"`.

### Старый подход (генератор мусора)
```csharp
public static double ParseSensorValueOld(string csvLine)
{
    // 3 аллокации строк в куче!
    string[] parts = csvLine.Split(';'); 
    // parts[1] — еще одна временная строка
    return double.Parse(parts[1], CultureInfo.InvariantCulture);
}
```

### Современный подход: 0 байт аллокаций
```csharp
public static double ParseSensorValueZeroAlloc(ReadOnlySpan<char> csvLine)
{
    // Ищем первый разделитель без аллокаций
    int firstSemi = csvLine.IndexOf(';');
    if (firstSemi < 0) return 0;

    ReadOnlySpan<char> remainder = csvLine.Slice(firstSemi + 1);
    
    // Ищем второй разделитель
    int secondSemi = remainder.IndexOf(';');
    ReadOnlySpan<char> valueSpan = secondSemi >= 0 
        ? remainder.Slice(0, secondSemi) 
        : remainder;

    // Парсим прямо из спана через ISpanParsable<double>
    if (double.TryParse(valueSpan, CultureInfo.InvariantCulture, out double result))
    {
        return result;
    }

    return 0;
}
```

Второй метод не выделяет в управляемой куче ни одного байта. На объёме в 100 000 RPS разница между этими двумя функциями — это гигабайты мусора в секунду против идеально плоской линии памяти.

## Резюме архитектуры

| Характеристика | `Span<T>` | `Memory<T>` |
|---|---|---|
| **Тип** | `ref struct` (только стек) | Обычный `struct` (стек или куча) |
| **Размер на x64** | 16 байт (ref + len) | 16 байт (object + index + length) |
| **Асинхронность** | Не может пересекать `await` | Идеально подходит для `async/await` |
| **Поддерживаемая память** | Стек, куча, нативная память | Куча (`T[]`, `string`), `MemoryManager` |
| **Доступ к элементам** | Прямой индексатор `span[i]` | Через свойство `.Span` |
