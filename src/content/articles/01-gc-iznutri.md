Мы весь цикл говорили "не аллоцируй в горячем пути", и пора объяснить, почему. Аллокация в .NET сама по себе почти бесплатна: это несколько инструкций и сдвиг указателя. Дорого стоит не она, а момент, когда выделенный кусок кончился. Тогда поток останавливается и зовет сборщик. Понимание того, как устроен этот механизм, отличает код, который просто работает, от кода, который держит хвосты latency.

Разберем по исходникам `src/coreclr/gc` и `src/coreclr/System.Private.CoreLib/src/System/GC.CoreCLR.cs`.

## На пальцах: что вообще делает сборщик

Прежде чем читать код, полезно понять задачу, которую решает GC.

В управляемых языках вы не освобождаете память руками. Вы создаете объекты, а когда они становятся не нужны, их должен кто-то убрать. Этим занимается **сборщик мусора** (garbage collector). Его работа состоит из трех шагов.

**Определить, что живо.** Объект считается живым, если до него можно добраться от **корней** (roots): локальных переменных на стеке, статических полей, регистров процессора. Все, до чего можно дотянуться по ссылкам от корней, называется **достижимым**. Остальное - мусор.

**Освободить мусор.** Память от недостижимых объектов возвращается в оборот.

**Прибрать.** Чтобы память не превратилась в швейцарский сыр из дырок, сборщик может **сжать** (compact) кучу: сдвинуть живые объекты вплотную друг к другу. Это называется компактировкой.

Проблема в том, что для первых двух шагов нужно точно знать, где лежат ссылки. Если сборщик ошибется и примет число за ссылку, он утащит мусорный указатель. Поэтому .NET использует **точное** отслеживание: JIT для каждого метода генерирует карту, где на каждом участке кода указано, какие слоты содержат ссылки.

И главное. Чтобы безопасно двигать объекты, сборщик должен на время **остановить все потоки** приложения. Эта остановка называется **паузой**. Вот почему мы весь цикл боремся с аллокациями: меньше мусора - реже сборки - короче суммарные паузы.

Отсюда и вся конструкция с поколениями. Идея в том, чтобы не проверять всю кучу каждый раз. Большинство объектов умирают молодыми, поэтому дешевле собирать только маленькую молодую область и не трогать старую. Так появляются gen0, gen1 и gen2.

## Словарь терминов

**Куча (heap)** - область памяти, где живут объекты.

**Аллокация** - выделение нового объекта в куче.

**GC (Garbage Collector)** - подсистема, которая находит недостижимые объекты и освобождает их память.

**Корень (root)** - точка, от которой отслеживается достижимость: локальная переменная, статическое поле, регистр.

**Достижимость** - свойство объекта, до которого можно добраться от корня по цепочке ссылок.

**Поколение (generation)** - gen0, gen1 или gen2. Чем выше номер, тем дольше объект живет.

**Эфемерный сегмент** - область, где вместе живут gen0 и gen1.

**SOH (Small Object Heap)** - куча обычных, небольших объектов.

**LOH (Large Object Heap)** - куча объектов от 85000 байт. Не компактируется по умолчанию.

**POH (Pinned Object Heap)** - куча для закрепленных объектов, которые сборщик не двигает.

**Пауза (pause)** - остановка потоков приложения на время сборки.

**Компактировка (compaction)** - сдвиг живых объектов, чтобы убрать дырки в памяти.

**Фрагментация** - разбиение памяти на мелкие куски из-за дырок между объектами.

**Write barrier** - код, который выполняется при записи ссылки в объект и помечает card как грязную.

**Card table** - битовая карта, отмечающая участки кучи, в которые недавно писали ссылки.

**Регион** - кусок кучи фиксированного размера, который можно отдать любому поколению.

**Server GC / Workstation GC** - два режима сборщика: многопоточный для серверов и однопоточный для клиентских приложений.

**Бюджет (budget)** - сколько байтов можно выделить в поколении до запуска сборки.

**Финализатор** - метод, который вызывается перед освобождением объекта, обычно для нативных ресурсов.

**Пиннинг** - запрет сборщику перемещать объект.

**Latency mode** - режим сборщика, управляющий частотой и типом сборок.

**Memory pressure** - сигнал сборщику, что нативная память занята и стоит прибраться активнее.

## Аллокация - это сдвиг указателя

У каждого потока есть свой контекст аллокации. Вот его структура (`gcinterface.h:201`):

```c
struct gc_alloc_context
{
    uint8_t*       alloc_ptr;
    uint8_t*       alloc_limit;
    int64_t        alloc_bytes;     // сколько SOH выделил этот контекст
    int64_t        alloc_bytes_uoh; // сколько UOH выделил этот контекст
    void*          gc_reserved_1;
    void*          gc_reserved_2;
    int            alloc_count;
};
```

Комментарий прямо над ней объясняет смысл (`gcinterface.h:198`):

```c
// The allocation context must be known to the VM for use in the allocation
// fast path and known to the GC for performing the allocation. Every Thread
// has its own allocation context that it hands to the GC when allocating.
```

`alloc_ptr` - указатель на следующий свободный байт, `alloc_limit` - где заканчивается текущий кусок. Быстрый путь аллокации объекта выглядит так:

1. загрузить `alloc_ptr`;
2. прибавить размер объекта с выравниванием;
3. сравнить с `alloc_limit`;
4. если влезло, записать новый `alloc_ptr` и указатель на method table;
5. вернуть объект.

Вот этот процесс на схеме. Пусть нужно выделить объект размером 24 байта:

```text
до аллокации:
  alloc_ptr   -------> [ free ............................. ]
                        ^                                  ^
                      alloc_ptr                        alloc_limit

после аллокации:
  alloc_ptr   -------> [ obj ][ free ...................... ]
                        ^      ^                           ^
                     вернули  alloc_ptr                 alloc_limit
```

Объект размером 24 байта занял первые 24 байта свободного куска, `alloc_ptr` сдвинулся на 24 вперед. Все, что произошло, - это одна операция сложения и одна запись.

Ни мьютексов, ни поиска свободного блока. Именно это JIT встраивает прямо в машинный код. Когда места не хватило, поток уходит в медленный путь `Alloc` (`gchelpers.cpp:270`), который заканчивается вызовом GC (`gchelpers.cpp:327`):

```c
retVal = GCHeapUtilities::GetGCHeap()->Alloc(pAllocContext, size, flags);
```

Комментарий рядом (`gchelpers.cpp:349`) описывает иерархию:

```c
// There are only two ways to allocate an object.
//     * Call optimized helpers that were generated on the fly. This is how JIT compiled code does most
//         allocations, however they fall back code:Alloc, when for all but the most common code paths.
//     * Call code:Alloc - When the jit helpers fall back, or we do allocations within the runtime code itself
```

Вот и весь секрет дешевизны аллокации. Пока `alloc_ptr < alloc_limit`, мы просто двигаем указатель. Проблема начинается, когда контекст исчерпан: потоку нужен новый кусок, а GC решает, дать ли его без сборки или сначала прибраться.

## Поколения: гипотеза о молодых объектах

GC строится на простом наблюдении: большинство объектов умирают молодыми. Поэтому память делится на поколения. Gen0 и gen1 живут вместе в одном эфемерном сегменте, gen2 отдельно. Границы эфемерного сегмента хранятся в полях `ephemeral_low` и `ephemeral_high` (`gc.cpp:906`):

```c
VOLATILE(uint8_t*)    gc_heap::ephemeral_low;
VOLATILE(uint8_t*)    gc_heap::ephemeral_high;
```

Зачем это разделение. Когда кончается бюджет gen0, GC собирает только gen0: обходит живые объекты в маленьком сегменте и переносит их в gen1. Это быстро, потому что gen0 мал. Объект, переживший сборку, получает шанс пожить в gen1. Переживший и gen1 уезжает в gen2, где его будут собирать уже в полную, дорогую сборку.

Вот как это выглядит в памяти. Gen0 и gen1 сидят в одном эфемерном сегменте, gen2 живет отдельно:

```text
эфемерный сегмент
+----------------------+----------------------+
|        gen0          |        gen1          |
+----------------------+----------------------+
   новые объекты         пережили одну сборку
   собирается чаще всего  собирается при gen1 GC

gen2 (отдельные сегменты или регионы)
+------------------------------------------------+
|  объекты, пережившие две сборки и больше       |
|  собирается только при полной сборке           |
+------------------------------------------------+
```

Путь объекта при сборках:

```text
new -> gen0 --(пережил gen0 GC)--> gen1 --(пережил gen1 GC)--> gen2
       |                              |                          |
     умер молодым              пожил дольше             живет долго
```

**Бюджет** - это сколько байтов можно выделить в поколении до запуска следующей сборки. Когда `alloc_ptr` в контексте потока доходит до предела, поток просит новый кусок, и GC смотрит: бюджет gen0 еще не исчерпан? Тогда просто дает память. Исчерпан? Тогда запускает сборку gen0. Именно поэтому аллокации "приближают" сборку: каждая из них уменьшает оставшийся бюджет.

Практический вывод: каждая лишняя аллокация в горячем пути не просто занимает память, она наполняет gen0 и приближает сборку. И если объект доживает до gen1 или gen2, стоимость его существования растет. Поэтому пулы, переиспользование и `stackalloc` бьют сразу по двум целям: не мусорят в gen0 и не дают объектам выживать.

## Три кучи: SOH, LOH, POH

В .NET не одна куча, а несколько, и они ведут себя по-разному.

SOH (Small Object Heap) - обычные объекты. Именно про него мы говорили выше: gen0, gen1, gen2, компактирующая сборка, объекты двигаются.

LOH (Large Object Heap) - объекты от 85000 байт. Вот эта константа (`gcinterface.h:246`):

```c
#define LARGE_OBJECT_SIZE ((size_t)(85000))
```

LOH не компактируется по умолчанию, потому что двигать большие объекты дорого. Отсюда фрагментация: массив на 100 КБ освободился, на его месте дырка, а новый массив на 120 КБ может туда не влезть, и куча растет. Компактировать LOH можно вручную через `GCSettings.LargeObjectHeapCompactionMode`, но это дорого.

POH (Pinned Object Heap) - отдельная куча для объектов, которые нельзя двигать. Она появилась именно потому, что пинить обычные объекты больно: закрепленный объект в SOH мешает компактировке и фрагментирует кучу. В POH объекты не двигаются по определению, и сборщик знает об этом заранее. Как туда попасть:

```csharp
byte[] buffer = GC.AllocateUninitializedArray<byte>(64 * 1024, pinned: true);
```

Флаг `GC_ALLOC_PINNED_OBJECT_HEAP` выставляется в `AllocateUninitializedArray` (`GC.CoreCLR.cs:860`):

```csharp
GC_ALLOC_FLAGS flags = GC_ALLOC_FLAGS.GC_ALLOC_ZEROING_OPTIONAL;
if (pinned)
{
    flags |= GC_ALLOC_FLAGS.GC_ALLOC_PINNED_OBJECT_HEAP;
}
```

А обычный `GCHandle.Alloc(obj, GCHandleType.Pinned)` пинит объект в его же куче и добавляет работу GC. Для долгоживущих буферов под interop POH лучше.

Сводка по трем кучам:

| Куча | Что там | Компактируется | Типичный размер объекта |
|---|---|---|---|
| SOH | обычные объекты | да | меньше 85000 байт |
| LOH | большие объекты | нет (по умолчанию) | 85000 байт и больше |
| POH | закрепленные объекты | не двигаются вообще | любой |

Практический пример, где это важно. Возьмем буфер для сетевого обмена:

```csharp
// плохо: 100 КБ уедет в LOH, где фрагментация
byte[] big = new byte[100_000];

// лучше: разбить на два буфера под порогом
byte[] part1 = new byte[50_000];
byte[] part2 = new byte[50_000];

// или взять из пула, тогда массив переиспользуется
byte[] pooled = ArrayPool<byte>.Shared.Rent(100_000);

// для interop, где нужен стабильный адрес: сразу в POH
byte[] pinned = GC.AllocateUninitializedArray<byte>(64 * 1024, pinned: true);
```

`ArrayPool` здесь не отменяет LOH: если рент вернет массив больше 85000, он все равно уедет в LOH. Но пул переиспользует его между запросами, поэтому новая память не выделяется и фрагментация не растет так быстро.

## Zeroing: скрытая стоимость new

`new byte[1_000_000]` не только выделяет память, но и зануляет ее. Для большого буфера это лишние мегабайты записи, которые вы все равно перезапишете данными. `GC.AllocateUninitializedArray` умеет это пропускать через флаг `GC_ALLOC_ZEROING_OPTIONAL` (`GC.CoreCLR.cs:857`).

Но там есть нюанс (`GC.CoreCLR.cs:832`):

```csharp
if (!pinned)
{
    if (RuntimeHelpers.IsReferenceOrContainsReferences<T>())
    {
        return new T[length];
    }

#if !DEBUG
    // small arrays are allocated using `new[]` as that is generally faster.
    if (length < 2048 / sizeof(T))
    {
        return new T[length];
    }
#endif
}
```

Если тип содержит ссылки, зануление обязательно: иначе GC увидит мусорные ссылки и упадет. Если массив маленький (меньше 2048 байт), обычный `new T[]` оказывается быстрее, чем поход в GC за неинициализированной памятью. Так что `AllocateUninitializedArray` имеет смысл для крупных буферов из простых типов, где зануление реально заметно.

## Write barrier и card table

Тут начинается самое интересное. Как GC узнает, какие старые объекты ссылаются на молодые, не сканируя всю gen2 на каждой сборке gen0? Через card table и write barrier.

Куча логически нарезана на небольшие участки, cards. Размер card выводится из размера страницы GC и ширины слова (`gcpriv.h:6778`). На каждую card есть бит в card table. Когда код записывает ссылку на объект, срабатывает write barrier: он помечает card, в которую попала запись, как грязную. В исходниках это видно по `card_bundle_set` и работе с `card_bundle_table` (`card_table.cpp:56`):

```c
void gc_heap::card_bundle_set (size_t cardb)
{
    uint32_t bits = (1 << card_bundle_bit (cardb));
    set_bundle_bits (&card_bundle_table [card_bundle_word (cardb)], bits);
}
```

При сборке gen0 GC не сканирует всю gen2. Он смотрит только грязные cards и находит ссылки оттуда. `card_bundle` - это второй уровень битовой карты, который позволяет пропускать целые чистые диапазоны одним махом, не проверяя каждую card.

Посмотрим на примере, для чего это. Пусть есть старый объект в gen2, который ссылается на молодой:

```csharp
class Node
{
    public Node? Next; // ссылочное поле
}

Node oldNode = GetLongLivedNode(); // живет в gen2
Node young = new Node();           // создан только что, в gen0

oldNode.Next = young; // вот здесь срабатывает write barrier
```

При сборке gen0 нужно понять, не ссылается ли кто-то из старой кучи на молодой объект. Без card table пришлось бы просканировать всю gen2. С card table достаточно посмотреть только грязные участки:

```text
gen2 в памяти, разбита на cards:
+-------+-------+-------+-------+-------+
| card0 | card1 | card2 | card3 | card4 |
| clean | dirty | clean | clean | dirty |
+-------+-------+-------+-------+-------+
          ^                             ^
     сюда писали                 сюда писали
   oldNode.Next = young
```

GC сканирует только `card1` и `card4`, находит ссылку на молодой объект в `card1` и учитывает ее. Остальная gen2 не трогается.

Как это выглядит на уровне кода, который генерирует JIT:

```csharp
// что вы пишете
oldNode.Next = young;

// что примерно делает JIT (упрощенно)
oldNode.Next = young;
CardTable.MarkCard(ref oldNode.Next); // write barrier помечает card
```

Карта делится не побайтово, а по участкам: один бит на card. Поэтому пометить card дешево, а на сборке можно пропустить целые чистые диапазоны. `card_bundle` добавляет еще один уровень: один бит на группу cards, чтобы быстро находить грязные области, не проверяя каждый бит.

Практический вывод: write barrier не бесплатен. Он срабатывает на каждую запись ссылки в объект. Чем меньше у вас ссылочных полей и чем реже вы их меняете, тем меньше работы для барьера. Структуры без ссылок (blittable) вообще не требуют барьера, и это еще одна причина любить их в горячем пути.

## Regions: новое поколение кучи

Долгое время куча была набором сегментов, и поколения жили в фиксированных местах. В современных .NET на 64-битных платформах включены regions (`gcpriv.h:153`):

```c
#define USE_REGIONS
```

Инварианты описаны прямо в комментарии (`gcpriv.h:137`):

```c
// Regions invariants -
//
// + each generation consists of 1+ regions.
// + a region is in a contiguous address range; different regions could have
//   gaps inbetween.
// + a region cannot contain more than one generation.
//
// This means any empty regions can be freely used for any generation.
```

Смысл в том, что регион - это кусок фиксированного размера, который можно отдать любому поколению. Освободился регион в gen2 - его можно отдать под gen0. Это убирает старую проблему, когда эфемерный сегмент заполнен мусором и его приходится расширять, а gen2 сидит на своих сегментах. С регионами GC может перекраивать кучу гораздо гибче. Плюс только с регионами работает динамическое число куч в server GC (`gcpriv.h:159`).

Вот разница на схеме. Со старыми сегментами поколения были привязаны к своим областям, а регионы можно перетасовывать:

```text
до: регионы распределены по поколениям
+--------+--------+--------+--------+--------+
| gen0   | gen0   | gen1   | gen2   | gen2   |
+--------+--------+--------+--------+--------+

после сборки: освободившийся регион gen2 отдан gen0
+--------+--------+--------+--------+--------+
| gen0   | gen0   | gen0   | gen1   | gen2   |
+--------+--------+--------+--------+--------+
                    ^
          был gen2, стал gen0
```

Правило из комментария "a region cannot contain more than one generation" означает, что внутри одного региона не может быть смеси поколений. Зато сам регион можно целиком перевести из одного поколения в другое. Это делает кучу гораздо более гибкой: GC не привязан к тому, что эфемерное поколение должно лежать в одном конкретном сегменте.

## Server GC против workstation

Есть два режима. Workstation GC - одна куча, сборки на потоке, который вызвал аллокацию, плюс фоновые сборки. Подходит для клиентских приложений, где важна отзывчивость и память.

Server GC - по куче на каждый процессор, отдельные потоки сборки для каждой кучи, параллельный маркинг и компактировка. Для серверов, которые держат много объектов и много ядер, это дает гораздо большую пропускную способность. Включается так:

```xml
<ServerGarbageCollection>true</ServerGarbageCollection>
```

или переменной окружения `DOTNET_gcServer=1`. Но у server GC выше базовое потребление памяти: у каждой кучи свои структуры. На маленьком контейнере это может быть неочевидно дорого.

Сравним режимы:

| Свойство | Workstation GC | Server GC |
|---|---|---|
| Куч | одна | по одной на процессор |
| Потоки сборки | поток, вызвавший аллокацию | отдельный поток на каждую кучу |
| Параллелизм | ограниченный | маркинг и компактировка параллельно |
| Память | меньше | больше, у каждой кучи свои структуры |
| Пропускная способность | ниже | выше на многопоточной нагрузке |
| Для чего | клиентские приложения, контейнеры с малым лимитом | серверы с большим числом ядер и объектов |

Отдельно про фоновые сборки. В workstation GC gen2 собирается в фоне, насколько это возможно, чтобы не морозить приложение надолго. Server GC тоже поддерживает фоновые сборки, но с отдельными потоками на кучу.

Как выбирать. Если у вас сервис на 8+ ядрах, который держит много объектов, server GC почти всегда выигрывает по пропускной способности. Если это маленький контейнер с лимитом памяти 256 МБ, server GC может съесть заметную долю на свои структуры, и workstation окажется экономнее.

## Как не будить сборщик

Соберем практические правила.

**Не аллоцируйте в горячем пути.** Пул буферов, переиспользование объектов, `stackalloc`, `Span<T>`. Это то, о чем мы говорили весь цикл.

**Держитесь под 85000 байт.** Массив на 90 КБ уедет в LOH, где нет компактировки и есть фрагментация. Иногда лучше разбить буфер на несколько меньших.

**Пиньте через POH, а не через GCHandle.** `GC.AllocateUninitializedArray<byte>(size, pinned: true)` не фрагментирует SOH и не мешает компактировке.

**Не зануляйте то, что перезапишете.** Для больших буферов из простых типов `GC.AllocateUninitializedArray` экономит реальную работу.

**Избегайте финализаторов.** Объект с финализатором переживает как минимум одну сборку, попадает в очередь финализатора и добавляет работу финализаторному потоку. Если финализатор не нужен, не заводите его. Если нужен, вызывайте `GC.SuppressFinalize` после детерминированной очистки.

**Для критичного по latency окна есть `NoGCRegion`.** Если у вас есть участок, где сборка недопустима, например обработка пакета в торговом ядре, можно попросить GC не собирать:

```csharp
if (GC.TryStartNoGCRegion(16 * 1024 * 1024))
{
    try
    {
        // работа, в которой недопустима пауза
    }
    finally
    {
        GC.EndNoGCRegion();
    }
}
```

Это работает только если вы заранее зарезервировали достаточно памяти, иначе регион молча завершится и вы получите `InvalidOperationException` при `EndNoGCRegion` (`GC.CoreCLR.cs:596`). Внутри региона аллокации продолжаются, но GC не запускается, пока вы не превысите бюджет.

**Для длительных пауз есть `GCSettings.LatencyMode`.** `SustainedLowLatency` заставляет GC откладывать полные блокирующие сборки (`GCSettings.cs:32`). Плата - потенциально большая куча и более резкая сборка, когда она все же случится.

## Как смотреть, что делает GC

Не угадывайте, измеряйте.

```csharp
GCMemoryInfo info = GC.GetGCMemoryInfo();
Console.WriteLine($"heap: {info.HeapSizeBytes}, committed: {info.TotalCommittedBytes}");
Console.WriteLine($"gen0: {GC.CollectionCount(0)}, gen1: {GC.CollectionCount(1)}, gen2: {GC.CollectionCount(2)}");
Console.WriteLine($"allocated total: {GC.GetTotalAllocatedBytes()}");
```

Живые метрики:

```powershell
dotnet-counters monitor --counters System.Runtime --process-id <PID>
```

Ключевые счетчики: `alloc-rate`, `gen-0-gc-count`, `gen-1-gc-count`, `gen-2-gc-count`, `time-in-gc`, `% time in GC`, `gen-0-size`. Если `alloc-rate` не падает после прогрева, где-то есть постоянный источник мусора.

Полезные переменные окружения:

- `DOTNET_gcServer=1` - server GC.
- `DOTNET_GCHeapHardLimit=0x40000000` - ограничить кучу (актуально в контейнерах).
- `DOTNET_GCConserveMemory=5` - агрессивнее отдавать память ОС, ценой CPU.
- `DOTNET_GCLOHThreshold=...` - изменить порог LOH (осторожно, меняет поведение GC).

## Ловушки

**`GC.Collect` в продакшене почти всегда ошибка.** Вы не знаете лучше сборщика, когда собирать. Единственное разумное применение - диагностика или явная точка в тестах. Ручная сборка полной кучи в горячем пути превращает плавную работу в пилу из пауз.

**`GC.KeepAlive` не запускает сборку.** Это барьер для JIT: он говорит "считай объект живым до этой точки". Нужен для interop, где нативный код держит указатель на управляемый объект, а JIT не видит причины держать его живым. К управлению GC это отношения не имеет.

**Финализатор не освобождает память.** Он выполняется на отдельном потоке через неопределенное время после того, как объект стал недостижим. Управляемая память освобождается только сборкой. Финализатор нужен для нативных ресурсов, и то обычно `SafeHandle` справляется лучше.

**`TryStartNoGCRegion` требует места.** Если свободной памяти меньше, чем вы просите, метод вернет `false`. Если во время региона память кончится, регион завершится, и `EndNoGCRegion` бросит исключение. Не используйте это как серебряную пулю.

**POH не бесконечен.** Долгоживущие запиненные буферы в POH остаются там, пока на них есть ссылки. Если вы запинили мегабайт и забыли отпустить, GC его не соберет и не сдвинет. Пул буферов в POH надо чистить.

## Частые ошибки на примерах

Соберу правила из практики в виде "было / стало".

**Аллокация в горячем цикле.**

```csharp
// было: массив на каждую итерацию
for (int i = 0; i < requests.Count; i++)
{
    byte[] temp = new byte[4096];
    Process(requests[i], temp);
}

// стало: буфер берется один раз из пула
byte[] temp = ArrayPool<byte>.Shared.Rent(4096);
try
{
    for (int i = 0; i < requests.Count; i++)
        Process(requests[i], temp);
}
finally
{
    ArrayPool<byte>.Shared.Return(temp);
}
```

**Крупный буфер уезжает в LOH.**

```csharp
// было: 100 КБ в LOH, фрагментация
byte[] big = new byte[100_000];

// стало: либо под порогом, либо из пула
byte[] pooled = ArrayPool<byte>.Shared.Rent(100_000);
```

**Пиннинг обычного массива.**

```csharp
// было: GCHandle на каждый interop-вызов
var handle = GCHandle.Alloc(buffer, GCHandleType.Pinned);
try
{
    NativeCall(handle.AddrOfPinnedObject());
}
finally
{
    handle.Free();
}

// стало: буфер в POH, пин почти бесплатен
byte[] pinned = GC.AllocateUninitializedArray<byte>(4096, pinned: true);
// дальше используем pinned без GCHandle
```

**Финализатор на каждый объект.**

```csharp
// было: объект с финализатором переживает сборку
class Wrapper
{
    ~Wrapper() => ReleaseNative();
}

// стало: SafeHandle, который освобождает детерминированно
class Wrapper : SafeHandleZeroOrMinusOneIsInvalid
{
    protected override bool ReleaseHandle() => ReleaseNative();
}
```

**`GC.Collect` в горячем пути.**

```csharp
// было: пила из пауз
foreach (var item in items)
{
    Process(item);
    GC.Collect(); // никогда так не делайте
}

// стало: доверьтесь сборщику, а давление сообщайте явно
foreach (var item in items)
    Process(item);
```

Если у вас большая нативная память, которую GC не видит, сообщите ему через `GC.AddMemoryPressure` и `GC.RemoveMemoryPressure`, а не через ручную сборку.

**`NoGCRegion` без запаса.**

```csharp
// было: если памяти не хватит, EndNoGCRegion кинет исключение
GC.TryStartNoGCRegion(1024);
// ...
GC.EndNoGCRegion();

// стало: проверяем, что регион реально начался
if (GC.TryStartNoGCRegion(16 * 1024 * 1024))
{
    try { /* работа без пауз */ }
    finally { GC.EndNoGCRegion(); }
}
else
{
    // запасной путь без гарантий
}
```

## Что в итоге

Аллокация - это сдвиг указателя в per-thread контексте. Дешево ровно до момента, когда `alloc_ptr` догоняет `alloc_limit`, и поток зовет GC. Дальше вступают поколения: gen0 собирается часто и дешево, gen2 редко и дорого. LOH хранит крупные объекты без компактировки, POH хранит запиненные без фрагментации SOH. Write barrier помечает cards, чтобы GC не сканировал всю старую кучу.

Отсюда и все наши правила: переиспользуй, держись под порогом LOH, пинь через POH, не зануляй зря, не заводи финализаторы. Каждое из них убирает работу, которую иначе сделал бы сборщик. А если совсем прижало по latency, есть `NoGCRegion` и `LatencyMode`, но это уже точечные инструменты под конкретную задачу.
